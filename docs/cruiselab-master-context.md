## What The Cruise Lab is

The Cruise Lab (thecruiselab.com) is Stuart Brodie's umbrella brand for a collection of free web tools built for the cruising community: "free web tools built by a cruiser, for cruisers." Each tool keeps its own name and identity as a member of "The Fleet"; the hub at thecruiselab.com is the landing page from which users pick a tool. New tools and services launch under the brand and get a card on the hub, with an "In the Lab" section teasing what's next. Most of the Fleet is free; **Forever Voyage** is the first *paid, bespoke* offering: a made-to-order keepsake website built for an individual customer's cruise. **Grand Voyage** (rev 26) is a free-play slot game whose bonuses showcase the Fleet. All tools carry a disclaimer that they are independent and not affiliated with or endorsed by Princess Cruises or any cruise line.

## Brand and design system

The visual identity was derived from the Sea You Soon app: a "casino at sea" look — midnight navy with champagne gold, Cinzel for display type, Outfit for body text. The hub's signature mark is a gold laboratory flask containing an animated sea (navy and sea-glass waves) with a single gold bubble.

CSS tokens used across Cruise Lab properties:

```css
--ocean-deep:#081830;  --ocean:#0d2445;
--panel:#122c52;       --panel-edge:#1d3d6b;
--gold:#d9b45c;        --gold-bright:#f0d087;  --gold-dim:rgba(217,180,92,.35);
--foam:#f3efe4;        --mist:#8fa2bd;
--seaglass:#46c3a8;    --seaglass-dim:rgba(70,195,168,.18);
--radius:14px;
```

Fonts: Cinzel (500/600/700) for headings, Outfit (300–700) for UI/body, loaded from Google Fonts. Headline treatment: gold vertical gradient text (gold-bright → gold) via background-clip. Section dividers: thin gold gradient rules with centred uppercase letterspaced labels. Cards: panel gradient background, panel-edge border, 14px radius, lift on hover with gold border. "Coming soon" cards: dashed border, sea-glass chip. Conventions: pure HTML/CSS/JS, single self-contained file per page where practical, no build step, no frameworks (Grand Voyage is the one exception with a tiny Python build step that inlines its maths engine and copies static assets: no frameworks, no npm). **Affiliate disclosure convention:** tools with affiliate links carry a discreet "may earn a commission" disclosure (GetMyCruiseConnection beside recommendation blocks + footer; Shore Thing screen-only footer line, excluded from print; link hub footer line). Keep disclosures when reworking copy; keep commission *mechanics* out of marketing copy.

Notes and lessons learned:
- **Never deploy from inside a `dist/` folder (proven 7 Oct 2026, Grand Voyage + personal registry).** Wrangler writes its `.wrangler/cache/` into the current working directory, so `cd dist && wrangler pages deploy .` leaves `dist/.wrangler/` behind, and the next deploy of `.` can upload it. Run from the project folder and pass `dist` as the path. (Only safe because these projects have no `functions/` folder: Functions are looked up in the working directory, so a project WITH Functions must deploy from inside its output folder and clear `.wrangler` there instead.)
- **A brand-new Pages project's hash deployment URL can be dead for a few minutes (proven 7 Oct 2026).** `https://<hash>.<project>.pages.dev` returned 0 bytes (no certificate yet) while `https://<project>.pages.dev` already served the exact build. Verify bytes on the canonical URL; the hash URL catches up.
- **Custom domain attach goes Initializing → Verifying → Active in about a minute on a same-zone domain (7 Oct 2026).** "Verifying" with a "Complete DNS setup" panel does NOT mean the record is missing: check the zone's DNS records (the CNAME was there, proxied) and wait for Active / SSL enabled.
- **A live-only Pages site with no local source / no repo is a recovery risk (proven 4 Sep 2026, norwaywithmum).** Direct-upload Pages **replaces the entire site** on each deploy, so you can't add one file without re-uploading the whole set — and if the source is gone, the "whole set" has to be reconstructed. Recovery path when there's no backup: mirror the live site (`mirror-norway-v1-20260904.py` at `~/cruiselab/` — downloads index.html + every same-origin asset it references, preserving paths, and reports a count + failures), verify the file count/size against the page, then deploy the full folder. Old deployments stay rolled-backable at their `<hash>.<project>.pages.dev` URL + the dashboard Rollback, so the live site is safe throughout. **Fix the root cause: every deployed site gets a git repo** (standing rule). Audit for other live-only sites in the account when convenient.
- **Reconstructing a whole site and re-deploying re-uploads everything (norwaywithmum: 95 files, ~146 MB, ~77s)** even if the bytes match a prior deploy — wrangler only hash-dedupes against deployments it can see for THAT project's recent history; a 3-month-old direct-upload may re-send in full. A high uploaded-file count that matches your expected total is the success signal, not a problem.
- **Claude's web fetch of Cruise Lab pages can be DAYS stale (proven 14 Jul 2026):** Anthropic-side fetches of thecruiselab.com returned a ~9-day-old 4-card hub even with a cache-busting query string, and returned 522 for a Forever Voyage page that curl'd 200 from Stuart's machine. **Never use Claude's fetch to verify (or panic about) a deploy — Stuart's curl/browser is canonical.** Claude-side fetch is fine for reading page *content* when freshness doesn't matter.
- **Edge-cache lag on a fresh deploy is normal (proven 15 Jul):** immediately after a deploy, a `curl` on the canonical domain can still return a `0`/stale grep even with a `?v=$(date +%s)` cache-buster. The reliable confirmations are (a) wrangler's **"Uploaded N files"** (N≥1 = something changed; 0 = nothing changed, check the branch), and (b) a `curl` on the specific `<hash>.<project>.pages.dev` deployment URL wrangler prints — that always serves the new build (except on a brand-new project, see above). The canonical domain catches up within minutes.
- **Creating a new Pages project:** the command is `npx wrangler pages project create <name> --production-branch=main`: NOT `wrangler pages create`. If the flag is omitted and wrangler falls into its interactive prompt, the prompt's suggested branch is `production`, which recreates the Forever Voyage trap; if that happens before anything is deployed, delete (`wrangler pages project delete <name>`) and recreate rather than living with it. (Grand Voyage's `cruiselab-slots` was created with `--production-branch=production` on purpose: always pass `--branch=production` for it.)
- **Never run `wrangler pages deploy` from `~`**: without a directory argument it tries to upload the current working directory — from home it dies on `~/.Trash` with a permissions error. Always pass the explicit folder path.
- **Production branches differ per project**: everything uses `main` except `forever-voyage` and `cruiselab-slots` (both `production`; the personal registry is also `production`). Deploying to the wrong branch silently creates a preview: the tell is an "alias URL" line in wrangler output. Verify with `curl -L` on the canonical `.pages.dev` URL after deploying.
- **pages.dev subdomains are a GLOBAL namespace**: if a name is taken by anyone anywhere, Cloudflare silently suffixes yours (project `oceanview` → oceanview-17z.pages.dev). Read the actual URL from wrangler output; never verify against an assumed name.
- **Local/ISP DNS can lag a fresh custom-domain attach (proven 15 Jul, All Aboard Store):** after a same-zone attach shows **Active / SSL enabled** in the dashboard, the authoritative Cloudflare nameserver resolves the record within ~90s, but Stuart's local/ISP resolver may not: a plain `dig +short <domain>` and `curl` return empty even though the site is live. Confirm at source with `dig +short <domain> @anuj.ns.cloudflare.com` (returns the Cloudflare IPs) and prove the site serves over the domain with `curl -sL --resolve <domain>:443:<IP> "https://<domain>/"`; Chrome works via Secure DNS regardless. This is cache propagation, not a config failure: do not re-attach or panic. (On 7 Oct, `slots.thecruiselab.com` resolved locally straight away.)
- **Facebook page setup quirks (14 Jul 2026):** a brand-new page has NO username — facebook.com/<name> shows "content isn't available" until one is set at Settings → General Page settings → Username (Facebook demands a password re-entry to save). Emoji pasted into the bio can save as `�` — re-paste and re-check after saving.
- **zsh: NEVER use `path` as a loop/script variable (proven 4 Sep 2026).** In zsh, lowercase `path` is tied to `$PATH` (they're the same array), so `path="$HOME/..."` silently overwrites PATH with a single directory — after which every external command (`cp`, `grep`, `awk`, `git`) fails with "command not found" while shell *builtins* (`echo`, `cd`) keep working. The tell: builtins succeed, externals don't; an `echo "✓ done"` line will lie because echo is a builtin. Same trap applies to `PATH`/`fpath`/`cdpath`/`manpath`. Fix: open a fresh tab (reloads config) or `export PATH="/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin:$PATH"`. Use a neutral name like `dest`. (Companion to the existing "no `#` comments in zsh code blocks" rule.)
- **Home-screen icon rollout (rev 24):** installing the icon kit on a project = drop `icons/` + `favicon.ico` + `manifest.webmanifest` into the project root, insert the head snippet before `</head>` in that project's root `index.html`, redeploy.
